# Keep local PostgreSQL clusters outside Haskell project checkouts

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.
Record friction met while implementing in the friction-log bundle as it occurs (see FRICTION.md).


## Purpose / Big Picture

Every Haskell project generated by the `nix-haskell-flake` module with `nix.postgresql = true`
keeps its development PostgreSQL cluster inside the checkout, at `./db/db`, with the server
log at `./db/postgres.log` and the server's UNIX socket in `./db`. A running PostgreSQL writes
to its data directory continuously (write-ahead log, checkpoints, statistics, the log file).
Every one of those writes is a file-system event inside the project tree, and on macOS each
event is delivered by `fseventsd` (the system daemon behind the FSEvents file-change API) to
every process watching that tree or one of its parents: editor and agent file watchers
(Codex, Claude Code), dev servers, Spotlight and Time Machine. On the author's machine
(2026-10-30) four such clusters were running under `~/Keikaku`, and `fseventsd` had grown to
about 33 GB of memory after 16 days of uptime; restarting it brought it down to 8 MB.

After this change, version 0.38.0 of the module places each checkout's cluster under the
user's XDG state directory, outside the source tree:

```text
${XDG_STATE_HOME:-$HOME/.local/state}/seihou/pg/<checkout-folder-name>-<checksum-of-checkout-path>/
  db/              # PGDATA, the cluster
  postgres.log     # PGLOG
  .s.PGSQL.5432    # the server socket (PGHOST is this directory)
```

The environment-variable contract (`PGHOST`, `PGDATA`, `PGLOG`, `PGDATABASE`,
`PG_CONNECTION_STRING`) is unchanged in name and meaning; only the paths move. Upgrading an
existing project with `seihou update nix-haskell-flake` runs a module migration that moves an
existing `./db` cluster to the new location, so no data is lost and no database is re-created.
If the cluster is still running, the migration refuses and says how to stop it.

To see it working: in an upgraded project, `echo $PGDATA` prints a path under
`~/.local/state/seihou/pg/`, `ls db` reports no such directory, `process-compose up` starts
PostgreSQL, and `psql -c 'select 1'` connects to the same data that used to live in `./db/db`.

## Decision Log

- Decision: Name each cluster directory `<checkout folder name, truncated to 32 bytes>-<POSIX
  cksum of the checkout's physical path>` instead of by `project.name`.
  Rationale: Several checkouts of one repository coexist on the author's machine (for example
  `kotei`, `kotei-plan107-acceptance` and `kotei-plan107-live` all have a `db/db` cluster), and a
  name-only key would make them share and corrupt one cluster. Module migrations also receive no
  template variables (see Context), so the migration script must derive the key from its
  working directory alone; the path-derived key satisfies that. The user chose this option on
  2026-10-30.
  Date: 2026-10-30

- Decision: Use POSIX `cksum` for the checksum.
  Rationale: The migration runs under `/bin/sh` outside the Nix dev shell, so it can rely only
  on base-system tools, while the shellHook runs inside the dev shell where Nix coreutils
  shadows the system tools. `cksum`'s default CRC algorithm is specified by POSIX and gives
  identical output from macOS `/usr/bin/cksum` and GNU coreutils 9.11 `cksum`
  (both print `2310145631 35` for `/Users/shinzui/Keikaku/bokuno/kotei`, checked 2026-10-30).
  `shasum`/`sha256sum` are not uniformly present on both sides.
  Date: 2026-10-30

- Decision: Move the whole PostgreSQL footprint (`PGHOST` socket directory, `PGDATA`, `PGLOG`),
  not only `PGDATA`, and keep using environment variables rather than leaving a `./db` symlink.
  Rationale: The log file is itself a steady event source. A symlink would keep `./db` paths
  working, but `.gitignore`'s `db/` pattern does not match a symlink, and tools that follow
  links would walk back into the cluster. Consumer scripts found on 2026-10-30 reference
  `db/db` only as fallbacks behind `PGDATA` (`keiro/justfile`, `keiro-runtime-kenshou/justfile`)
  or in an error message (`koyomi/scripts/process-up.sh`), so they keep working inside the dev
  shell.
  Date: 2026-10-30

- Decision: Keep the `db/` line in the generated `.gitignore`.
  Rationale: It still ignores a legacy cluster that has not been migrated yet, or one left
  behind when a migration refused, and removing it gains nothing.
  Date: 2026-10-30

## Context and Orientation

This repository, `mori://shinzui/seihou-modules`, is a Seihou registry: a collection of
modules that the `seihou` CLI (`mori://shinzui/seihou`, installed locally as
`seihou v0.13.0.0`) renders into consumer projects. A module is a directory containing a
`module.dhall` (written in Dhall, a typed configuration language) that declares variables,
prompts, template steps and migrations, plus a `files/` directory of templates. Templates use
`{{var}}` substitution and `{{#if …}}` conditionals.

The module changed by this plan is `modules/haskell/nix-haskell-flake/`, currently version
`0.37.0`. The files that matter:

- `modules/haskell/nix-haskell-flake/module.dhall`: declares the variables (including
  `nix.postgresql`, `nix.pg-database`, `nix.pg-package`), the template steps, and a
  `migrations` list spliced onto the module record with `//`. Existing edges are
  0.10.0 → 0.11.0 (a `DeleteFile`) and 0.34.0 → 0.35.0 (a one-line `RunCommand` written as a
  Dhall double-quoted string). A local `MigrationOp` union type is declared at the top of the
  file because the pinned `seihou-schema` predates migrations.
- `modules/haskell/nix-haskell-flake/files/nix/haskell.nix.tpl`: renders to the consumer's
  `nix/haskell.nix`. Its `shellHook` Nix string contains, under `{{#if Eq nix.postgresql true}}`,
  the block this plan changes:

  ```bash
  export PGHOST="$PWD/db"
  export PGDATA="$PGHOST/db"
  export PGLOG=$PGHOST/postgres.log
  export PGDATABASE={{#if IsSet nix.pg-database}}{{nix.pg-database}}{{#else}}{{project.name}}{{/if}}
  export PG_CONNECTION_STRING="postgresql://$(jq -rn --arg x "$PGHOST" '$x|@uri')/$PGDATABASE"

  mkdir -p "$PGHOST"
  mkdir -p .dev

  if [ ! -d "$PGDATA" ]; then
    initdb --auth=trust --no-locale --encoding=UTF8
  fi
  ```

  The shellHook is a Nix indented string (`'' … ''`), so a literal shell `${` must be written
  `''${` (the file already does this for `CPATH`).
- `modules/haskell/nix-haskell-flake/files/process-compose.yaml.tpl`: the `postgres` process
  runs `pg_ctl start -w -l $PGLOG -o "--unix_socket_directories='$PGHOST'" …` and stops with
  `pg_ctl stop -D $PGDATA`. It refers only to the environment variables and needs no change.
- `modules/haskell/nix-haskell-flake/files/envrc.tpl`: the generated `.envrc` runs
  `use flake` then `eval "$shellHook"` from the project root, so `$PWD` in the shellHook is the
  checkout root under direnv.
- `modules/haskell/nix-haskell-flake/files/gitignore-haskell.tpl`: contains `db/`.
- `modules/haskell/nix-haskell-flake/README.md`, `okf-docs/modules/nix-haskell-flake.md`,
  `README.md` (registry table), `mori.dhall` and `seihou-registry.dhall` all carry the module
  version string `0.37.0`; the module README also has a migration table near line 404 listing
  each `from`/`to` edge. Commit `0a95b38` (the 0.37.0 release) shows every file a release
  touches.

How Seihou runs a `RunCommand` migration op (read from `mori://shinzui/seihou`,
`seihou-core/src/Seihou/Engine/Migrate.hs` and `docs/user/migrations.md`; artifact-level URIs
pending):

- The `run` text is passed verbatim to `/bin/sh -c`. There is **no** template-variable
  substitution, so `project.name` and `nix.postgresql` are not available to the script. The
  process inherits Seihou's environment (`HOME`, `XDG_STATE_HOME`). When `workDir` is `None`
  the command runs in Seihou's working directory, which is expected to be the project root but
  must be confirmed in Milestone 1.
- Standard output is discarded. A non-zero exit aborts the migration chain, prints the
  command's standard error (or the command text if stderr is empty), and does not write the
  manifest, so the user can fix the cause and rerun.
- Migrations apply to every project that has the module recorded, regardless of variable
  values. The script must therefore be a no-op in projects that never enabled PostgreSQL.
- `seihou update` plans migrations in a staging simulation where commands are not executed
  (it reports "includes non-simulatable commands") and runs them for real during publication
  (`runRealMigrations` in `seihou-cli/src/Seihou/CLI/Update.hs`).
- The window walker applies an edge whenever its `[from, to]` range lies within
  `[installed, target]`. A consumer on 0.35.0 updating to 0.38.0 still runs the
  0.37.0 → 0.38.0 edge.

Consumers. On 2026-10-30, under `~/Keikaku/bokuno`, 23 checkouts that record
`nix-haskell-flake` in `.seihou/manifest.json` had a `db/db` cluster, among them `keiro`,
`kioku`, `kotei` (plus two extra `kotei` checkouts) and `mori-project/mori`. Four clusters
were running. `libraries/pgmq-hs-project/pgmq-hs` keeps its cluster at `.dev/db/data` through
its own wiring; it is not generated by this module and is out of scope.

ADRs. The relevant local ADRs are:

- [docs/adr/1-use-project-local-sockets-for-redis-development-services.md](../adr/1-use-project-local-sockets-for-redis-development-services.md)
  chose a checkout-local Redis socket for isolation and discoverability and noted the macOS
  104-byte UNIX-socket path limit. This plan keeps Redis as is. For PostgreSQL it trades some
  discoverability for removing a constant write load from the source tree. The isolation
  property is preserved by keying the directory on the checkout path. The new socket path is
  short and does not depend on how deep the checkout is:
  `/Users/<user>/.local/state/seihou/pg/<≤32 bytes>-<≤10 digits>/.s.PGSQL.5432` is at most
  about 100 bytes for a short home directory, versus a checkout-depth-dependent path today.
- [docs/adr/3-separate-managed-scaffold-nix-wiring-from-user-extensions.md](../adr/3-separate-managed-scaffold-nix-wiring-from-user-extensions.md):
  managed files such as `nix/haskell.nix` are regenerated, and user overrides belong in
  `flake.module.nix` or `.envrc.local`. This change edits only managed templates.

No existing ADR covers where service state lives; Milestone 3 adds one.

### Milestone 2: ship 0.38.0

Edit `modules/haskell/nix-haskell-flake/files/nix/haskell.nix.tpl`, replacing the PostgreSQL
block shown in Context with one that computes the state directory and guards against a legacy
cluster. Keep the variable names, and keep `mkdir -p .dev` because process-compose logs there:

```bash
# The local cluster lives outside the checkout, so PostgreSQL's constant
# writes do not reach file watchers on the source tree. One directory per
# checkout: <folder name>-<cksum of the physical checkout path>.
pg_checkout="$(pwd -P)"
pg_state="''${XDG_STATE_HOME:-$HOME/.local/state}/seihou/pg"
export PGHOST="$pg_state/$(printf '%.32s' "$(basename "$pg_checkout")")-$(printf %s "$pg_checkout" | cksum | cut -d' ' -f1)"
export PGDATA="$PGHOST/db"
export PGLOG="$PGHOST/postgres.log"
export PGDATABASE=…   # unchanged
export PG_CONNECTION_STRING=…   # unchanged

mkdir -p "$PGHOST"
mkdir -p .dev

if [ -f "$pg_checkout/db/db/PG_VERSION" ] && [ ! -d "$PGDATA" ]; then
  echo "nix-haskell-flake: ./db/db holds a cluster from module < 0.38.0 that has not been moved to $PGDATA." >&2
  echo "nix-haskell-flake: stop it and run 'seihou migrate nix-haskell-flake'; not running initdb." >&2
elif [ ! -d "$PGDATA" ]; then
  initdb --auth=trust --no-locale --encoding=UTF8
fi
unset pg_checkout pg_state
```

The guard matters because without it a project regenerated without its migration (for
example a template render that bypassed migrations, or a failed migration whose templates
were nevertheless published) would silently `initdb` an empty cluster at the new location
and the user would see an empty database. With the guard, `pg_ctl start` fails because
`PGDATA` does not exist, and the warning explains why.

Add the migration edge in `modules/haskell/nix-haskell-flake/module.dhall`, appended to the
`migrations` list after the 0.34.0 → 0.35.0 entry, with a comment in the style of the existing
ones. The command is one POSIX `sh` script. Write it as a Dhall multi-line literal (`'' … ''`),
in which a literal `${` must be escaped as `''${`. The script must compute the directory
exactly as the shellHook does:

```sh
set -eu
# Nothing to do unless this checkout has a pre-0.38.0 cluster.
[ -f db/db/PG_VERSION ] || exit 0
if [ -f db/db/postmaster.pid ]; then
  pid=$(head -n 1 db/db/postmaster.pid)
  if kill -0 "$pid" 2>/dev/null; then
    echo "nix-haskell-flake 0.38.0 moves ./db out of the checkout, but PostgreSQL (pid $pid) is running from ./db/db. Stop it (process-compose down, or pg_ctl stop -D db/db inside the dev shell) and rerun." >&2
    exit 1
  fi
fi
checkout=$(pwd -P)
dest="${XDG_STATE_HOME:-$HOME/.local/state}/seihou/pg/$(printf '%.32s' "$(basename "$checkout")")-$(printf %s "$checkout" | cksum | cut -d' ' -f1)"
if [ -e "$dest/db" ]; then
  echo "nix-haskell-flake: both ./db/db and $dest/db exist; keep one and remove the other, then rerun." >&2
  exit 1
fi
mkdir -p "$dest"
rm -f db/.s.PGSQL.*            # stale socket and lock files from an unclean stop
mv db/db "$dest/db"
if [ -e db/postgres.log ]; then
  if [ -e "$dest/postgres.log" ]; then mv db/postgres.log "$dest/postgres.pre-0.38.0.log"
  else mv db/postgres.log "$dest/postgres.log"; fi
fi
rmdir db 2>/dev/null || echo "nix-haskell-flake: left ./db in place because it contains other files." >&2
```

Notes for the implementer. `kill -0` succeeds only for a live process the user can signal,
so a stale `postmaster.pid` from a crash lets the move proceed, which is correct: PostgreSQL
removes a stale pid file on its next start. `mv` within one APFS or ext4 volume is a rename and
is instant. Across volumes it copies, which is still correct while the server is stopped.
The message on the last line goes to stderr but is only shown if the command fails. That is
acceptable because the leftover directory is harmless and gitignored.

Bump `version` in `module.dhall` to `0.38.0` and prepend one sentence to the module

## Validation and Acceptance

The change is accepted when all of the following are observed:

- In a fixture project upgraded from 0.37.0 with a stopped cluster, `seihou update
  nix-haskell-flake` succeeds, `./db` is gone, and a row inserted before the upgrade is read
  back after it through the new dev shell's `PG_CONNECTION_STRING`.
- With the cluster running, the same update exits non-zero with the "is running from ./db/db"
  message and leaves `./db/db` untouched.
- A project without PostgreSQL updates with no effect on the state directory.
- A fresh 0.38.0 project never creates `./db`.
- A legacy cluster with 0.38.0 templates produces the warning and no empty cluster.
- One real consumer (`kioku` or another chosen at implementation time) keeps its data
  across the upgrade.

The goal of this work, less file-system event traffic, is not separately benchmarked.
Optionally, `sudo fs_usage -w -f pathname postgres` before and after shows PostgreSQL writes
moving out of `~/Keikaku`. That check is a confirmation, not an acceptance gate.


## Idempotence and Recovery

The migration is idempotent. Once `./db/db/PG_VERSION` is gone it exits 0 immediately, so a
rerun after success, or after a refusal, is safe. It changes nothing before its two
refusal checks (running server, existing destination), so a refusal leaves the checkout
exactly as it was. After the `mv` of `db/db` succeeds, the only remaining steps move the log
and remove an empty directory. Failures there cannot lose cluster data.

Manual rollback for one checkout, with the server stopped:

```bash
dest=$(nix develop -c sh -c 'echo $PGHOST')   # or read $PGHOST in the direnv shell
mkdir -p db && mv "$dest/db" db/db && mv "$dest/postgres.log" db/ 2>/dev/null; rmdir "$dest"
```

then revert the consumer's upgrade commit (or `git restore` the generated files and
`.seihou/manifest.json`) so its shellHook points at `./db` again.

The fixture test uses temporary directories for both projects and `XDG_STATE_HOME`, so
it can be rerun freely.


## Interfaces and Dependencies

- Consumer contract (unchanged names): `PGHOST` (socket directory), `PGDATA`, `PGLOG`,
  `PGDATABASE`, `PG_CONNECTION_STRING`. New values derive from
  `${XDG_STATE_HOME:-$HOME/.local/state}/seihou/pg/<key>`, where `<key>` is the first 32 bytes of
  the checkout folder name, a hyphen, and the decimal CRC printed by `cksum` for the physical
  checkout path with no trailing newline. The shellHook and the migration must keep computing
  this identically; the fixture test asserts it.
- `seihou` ≥ 0.13.0.0 for `seihou update` migration staging and `RunCommand` execution
  (`mori://shinzui/seihou`).
- Base-system tools in the migration: `/bin/sh`, `cksum`, `basename`, `head`, `kill`,
  `mv`, `rmdir`, `printf`, all POSIX.
- No change to `flake.nix.tpl`, `files/flake.lock`, or any pinned input, so
  `scripts/update-nix-haskell-flake-lock.sh` does not need to run.
