# Mount the keiro-ui inspection surface in the haskell-keiro-project server starter

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.
Record friction met while implementing in the friction-log bundle as it occurs (see FRICTION.md).


## Purpose / Big Picture

keiro-ui (`mori://shinzui/keiro-ui`) is a browser console that inspects a running Keiro
service: it lists the service's aggregates, shows the folded state of one aggregate instance,
lists projection rebuild groups, follows live event feeds over WebSocket, and shows Kiroku
event-store metrics. It reads all of this over HTTP from a service-hosted "inspection surface":
Keiro operations mounted under the URL prefix `/keiro` and Kiroku metrics mounted under
`/kiroku`, served on a separate, private, read-only listener port.

Today a service generated by this repository's `haskell-keiro-project` module has no such
surface. The one service that has it, `mori://tan/chapter-service-v2`, wrote it by hand and
registered each aggregate by hand, so a newly added aggregate silently goes missing from the
console. After this plan, every freshly generated Keiro project contains the inspection code
in its server package from the first render, the set of inspectable aggregates comes from
keiro-dsl's generated catalog (so every aggregate the domain declares is mounted
automatically), and whether the listener runs is a runtime setting. The module gains two
options so that a composing recipe can choose the built-in default of that setting and the
default port.

To see it working, an implementer renders a project from the module, adds a two-aggregate
fixture domain, regenerates code with the released keiro-dsl, and starts the inspection
listener with `INSPECTION_ENABLED=true`. Then:

```bash
curl -s http://127.0.0.1:9094/keiro/health
curl -s http://127.0.0.1:9094/keiro/aggregate/types
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9094/kiroku/health
```

returns a Keiro health object whose `status` is `ok`, an `items` array naming both fixture
aggregates, and `200`. With the setting left at its default (`false`) nothing listens on 9094.

This plan is one of four independent ExecPlans linked only through Mori plan dependencies.
It hard-depends on
`mori://shinzui/keiro/plans/336-generate-an-aggregate-inspector-catalog-for-every-keiro-dsl-aggregate`
(called "plan A" below), which makes keiro-dsl generate the catalog and ships it in a keiro
release. Its consumer is
`mori://tan/tan-seihou-modules/plans/7-enable-keiro-ui-inspection-by-default-in-the-tan-keiro-project-recipe`
(called "plan C" below), which will set the two new module options from the TAN recipe. A
sibling, `mori://tan/chapter-service-v2/plans/1-adopt-the-generated-aggregate-inspector-catalog-in-chapter-service-v2`,
adopts the same generated catalog in the reference service; nothing here depends on it.

## Surprises & Discoveries

- Observation: the starter has no assembled server runtime to "mount" anything into. It seeds
  only `{{project.namespace}}.Server.App` (`serviceServer`, `mkApp` with injected health
  probes); it has no Settei `Settings`, no `Runtime`/`Boot` module, no executable and no Keiro
  dependency at all (core depends only on `base` and `lens`). Those are written later by the
  implementer or the `haskell-keiro-service` blueprint, following the generated brief
  `docs/bootstrap-keiro.md`. This forced the split described in the Decision Log: the seed
  ships self-contained, compiled inspection plumbing plus a Settei settings fragment, and the
  brief makes wiring it into the server executable a required implementation step.
  Evidence: `modules/haskell/haskell-keiro-project/files/server.hs.tpl`,
  `files/server.cabal.tpl`, `files/core.cabal.tpl`, and
  [ADR 2](../adr/2-separate-keiro-project-seeds-from-domain-implementation.md) ("The seed does
  not pretend to implement an assembled application runtime").

- Observation: keiro-dsl's Cabal fragment exposes only one generated "facade" module and puts
  every other generated module, including `Generated.ReplayAudit` and
  `Generated.ProjectionCatalog`, in `other-modules`, so the server package cannot import them.
  Evidence: `renderManifestForServiceWithFacade` in `keiro-dsl/src/Keiro/Dsl/Manifest.hs` of
  `mori://shinzui/keiro` (artifact-level URI pending), and
  `chapter-service-v2-core/chapter-service-v2-core.cabal` of `mori://tan/chapter-service-v2`
  (artifact-level URI pending), where both modules are listed under `other-modules`. Plan A's
  `Generated.Inspection` is expected to be hidden the same way; Milestone 0 confirms it.

- Observation: keiro-ops refuses every command unless the database schema matches the binary,
  and its schema check only supports PostgreSQL 18. The reference service passed with the
  module's default `nix.pg-package = "postgresql"`, so the pinned nixpkgs default is believed
  to be 18; Milestone 0 confirms it with `postgres --version` inside a generated shell.
  Evidence: `mori://shinzui/jinmyaku/okf/adrs/concepts/ADR-14` and `RefuseOnDrift` handling in
  `keiro-ops-http/src/Keiro/Ops/Http/Application.hs` of `mori://shinzui/keiro`
  (artifact-level URI pending).

- Observation: plan A, as drafted on 2026-11-16, confirms the four exports and adds three
  facts that shape this plan. Absent sections are empty values, not `Maybe`: an
  aggregates-only context gets an empty validated projection catalog and a projections-only
  context gets an empty inspector list and map. A context with neither aggregates nor
  projections emits no `Generated.Inspection` module at all, so the shared-only seed workspace
  never has one; the seed form of the core re-export (Decision Log) is therefore required, and
  the brief must say to switch to the domain form only after a scaffold has emitted the
  module. There is one module per context, which is one per workspace scaffold run. Plan A adds
  no keiro-ops helper: hooks are built from `Keiro.Ops.emptyAppHooks`. The generated
  `aggregateInspectors` value clashes with the library function
  `Keiro.Inspection.Aggregate.aggregateInspectors`, so code that sees both must import the
  library module qualified. Plan A proposes the release as keiro 0.25.1.0 (additive, no DSL
  language bump); the version actually pinned is whatever plan A records at completion.
  Evidence: coordinator summary of
  `mori://shinzui/keiro/plans/336-generate-an-aggregate-inspector-catalog-for-every-keiro-dsl-aggregate`.


## Decision Log

- Decision: the seed always contains the inspection code; enablement is the Settei setting
  `inspection.enabled`, whose built-in default comes from the new module option
  `inspection.enabled-default` (default `false`), and whose port default comes from
  `inspection.port` (default `9094`).
  Rationale: this is the contract plan C builds on; a compile-time option would fork the
  generated source and make later enablement a code change.
  Date: 2026-11-16

- Decision: the inspection plumbing is seeded as compiled, self-contained server-library
  modules (`Server.Inspection`, `.Hooks`, `.Listener`, `.Origin`, `.Settings`) that the seed
  builds and tests on its own, exactly like the seeded health-probe assembly; the server
  executable written during implementation must call `withInspection` around its API
  listener, and the brief makes that a required step with its own acceptance.
  Rationale: the seed has no runtime to edit (see Surprises), and ADR 2 keeps runtime
  assembly out of the seed while requiring shared HTTP plumbing to work in a fresh seed.
  Date: 2026-11-16

- Decision: the server reaches plan A's hidden generated module through a starter-owned,
  exposed re-export module in core, `{{project.namespace}}.Inspection`, which exports the same
  four names with the same types as plan A. Its seed form defines an empty catalog so the
  fresh seed compiles before any domain exists; after the first `just keiro-scaffold` the
  implementer replaces its body with a re-export of the generated module (the exact text is
  given in the brief). `Server.Inspection.Hooks` imports only this module and never names a
  hand-written aggregate.
  Rationale: a module in core may import core's own `other-modules`; the seed cannot name
  the generated module statically because its path contains the PascalCase DSL context, which
  Seihou templates cannot compute, and because it does not exist until keiro-dsl runs. Plan A
  emits no module for a context with neither aggregates nor projections, so the switch happens
  only after the first scaffold that actually produces `Generated.Inspection`.
  Date: 2026-11-16

- Decision: the environment variables are unprefixed: `INSPECTION_ENABLED`,
  `INSPECTION_HOST`, `INSPECTION_PORT`, `INSPECTION_ALLOWED_ORIGINS`, bound to the keys
  `inspection.enabled`, `inspection.host`, `inspection.port`, `inspection.allowedOrigins`.
  Rationale: the starter has no existing environment prefix; the Settei service standard
  (`mori://shinzui/keiro-runtime-patterns/docs/config-settei-service-standard`) and the
  blueprint's reference `Settings.hs` use unprefixed names (`HTTP_PORT`, `DATABASE_HOST`);
  Seihou templates cannot derive an upper-snake prefix from `project.name`; and adding a
  prefix option would widen plan C's contract. The bindings are exported as one validated
  `Bindings` group that the service merges with `mergeBindings`.
  Date: 2026-11-16

- Decision: do not add a `nix.pg-package` binding to the module's `nix-haskell-flake`
  dependency even if Milestone 0 finds a PostgreSQL major other than 18; document
  `--var nix.pg-package=postgresql_18` instead.
  Rationale: adding a binding to a released dependency makes Seihou lose the saved inputs of
  existing projects and breaks `seihou update`
  ([FRIC-10](../friction-log/10-seihou-treats-a-new-dependency-binding-as-a-new-instance-and-breaks-update.md),
  promoted to `mori://shinzui/seihou/okf/improvement-requests/concepts/IR-15`).
  Date: 2026-11-16

## Context and Orientation

This repository (`mori://shinzui/seihou-modules`) publishes Seihou modules. Seihou is a
project scaffolder: a module is a directory with a `module.dhall` descriptor that declares
input variables ("options", for example `project.name`), prompts, dependencies on other
modules, and steps; each step renders a template file (`*.tpl`, with `{{var}}` substitution
and `{{#if Eq var true}} … {{#else}} … {{/if}}` conditionals) or copies a file into the target
project. A step with `lifecycle = Some "seed"` is a "seed": it is written once when absent and
afterwards belongs to the project, so later `seihou update` runs never change it. Steps
without that lifecycle are "managed" and are updated on every run.

The module this plan changes is `modules/haskell/haskell-keiro-project` (version `0.4.1` in
`modules/haskell/haskell-keiro-project/module.dhall`). It generates a six-package Haskell
"seed" for a Keiro service: `<name>-core`, `-api`, `-migrations`, `-workers`, `-server`,
`-client`, plus a keiro-dsl workspace under `domain/`, a justfile, a Nix shell (through its
dependency on `modules/haskell/nix-haskell-flake`, with PostgreSQL and process-compose on),
Hurl/Hinagata test tooling and an optional `mori.dhall`. Keiro is the event-sourcing runtime
(`mori://shinzui/keiro`); keiro-dsl is its code generator, which turns `.keiro` domain
specifications into Haskell modules under `<name>-core/src`, prints a Cabal "fragment" (module
lists, extensions, dependencies) that the developer pastes into the core Cabal file, and
leaves hand-owned "hole" modules whose stubs compile but call `error` until filled. Almost
every module step is a seed, so existing projects will not receive changes to existing files
(see Idempotence and Recovery). The relevant templates are, all under
`modules/haskell/haskell-keiro-project/files/`:

`server.hs.tpl` renders `<name>-server/src/<Ns>/Server/App.hs`, exporting `serviceServer` and
`mkApp liveCheck readyCheck`; `server.cabal.tpl` declares the server library (base,
`<name>-core`, `<name>-api`, servant-health, servant-server, wai) and the
`<name>-server-health` test suite built from `health-test.hs.tpl`; `core.cabal.tpl` declares a
core library depending only on base and lens with modules `<Ns>.Bootstrap` and `<Ns>.Prelude`;
`cabal.project.tpl` pins `index-state: {{haskell.index-state}}` (option default
`2026-10-26T00:00:00Z`) and `with-compiler: ghc-9.12.4`; `justfile.tpl` holds `keiro-check`,
`keiro-scaffold` (runs `.bin/keiro-dsl scaffold domain/<name>.keiro-workspace --out
<name>-core/src --runtime-package <name>-core ...`) and test recipes; `mori.dhall.tpl` is the
optional dependency inventory; `bootstrap.md.tpl` renders `docs/bootstrap-keiro.md`, the
implementation brief that the `blueprints/haskell-keiro-service` blueprint tells an agent to
follow (the blueprint's `prompt.md` says "Read that generated brief in full and carry out its
workflow"); `README.md.tpl` is the generated project README; `nix/keiro-dev-tools.nix.tpl` is
the one managed Nix file and only adds tools. The module's own documentation is
`modules/haskell/haskell-keiro-project/README.md`. The starter pins no Keiro version today; the
brief tells the implementer to choose a verified released cohort.

The blueprint `blueprints/haskell-keiro-service/blueprint.dhall` (version `0.4.0`) repeats the
module's variables, including a `haskell.index-state` default, and uses the module as its base.

Generated Nix shells use the "bare shell" path by default: Cabal resolves every Haskell
dependency from Hackage at the pinned index-state. Projects that opt into a retained runtime
from `mori://shinzui/haskell-nix` get prebuilt packages from a cohort; the current
`rei-keiro-0.24` cohort already lists keiro-ops, keiro-ops-http and kiroku-metrics as first
party (`generated/profiles/rei-keiro-0.24/cohort-versions.nix`, artifact-level URI pending),
but no `keiro-runtime` generation yet selects keiro 0.25 or later (generation 8 is the 0.24
cohort). A generation retaining plan A's release is an external precondition owned by
`mori://shinzui/haskell-nix` for projects that select a retained runtime (the reference
service does, in its unmanaged `flake.module.nix`); it is not needed for this plan's
acceptance, which uses the bare shell. Note also that keiro 0.24 to 0.25 contains a breaking
durable-tracing change, so a project still on the 0.24 cohort cannot adopt this surface by
bumping only the inspection packages; the starter itself pins no keiro version today, so a
fresh render is unaffected.

The module is tested by two scripts at the repository root. `python3
scripts/check-keiro-bootstrap.py` renders the module into temporary directories with `seihou
run haskell-keiro-project --no-save-prompted --no-commands --var ...` (copying the module, the
Nix module and the blueprint into the temp project's `.seihou/modules`), asserts on the
rendered files, runs `cabal check`, checks the `mori.dhall` inventory against the Cabal files
using `scripts/keiro-dependency-owners.json` (Cabal package name to Mori owner), checks rerun
idempotence and seed edit protection, and type-checks `seihou-registry.dhall` and `mori.dhall`.
`python3 scripts/test-keiro-bootstrap.py --live` renders once, enters `nix develop` in the
rendered project and runs `cabal build all`, `cabal test all`, OpenAPI checks, and a temporary
`acceptance` consumer executable against a private PostgreSQL cluster. Its `consumer`
function is the pattern for this plan's acceptance executable. The module version also
appears in `seihou-registry.dhall` and in the `haskell-keiro-project` template entry of
`mori.dhall`.

The reference implementation is commit `43e2a93` ("feat(server): mount the keiro-ui
inspection surface") of `mori://tan/chapter-service-v2`; read it with `git -C "$(mori path
mori://tan/chapter-service-v2)" show 43e2a93`. Its project-relative files (artifact-level URIs
pending) are `chapter-service-v2-server/src/ChapterServiceV2/Server/Inspection.hs` (the
composed application), `Server/Inspection/Hooks.hs` (operational hooks), `Server/Inspection/Listener.hs`
(the private Warp listener), `Server/Inspection/Origin.hs` (browser-origin validation and the
WebSocket origin guard), `Server/Config.hs` (the `inspection.*` Settei settings and a small
inspection store), `Server/Runtime.hs` (wraps the API `runSettings` in `withInspection`),
`test/FirstHttp.hs` (HTTP checks), `docs/api/server-operations.md`,
`config/local-chapters.example.yaml`, and `flake.module.nix` (image `ExposedPorts` gains
`9094/tcp`). Its `chapter-service-v2-core/src/ChapterServiceV2/Domain/Inspection.hs` lists
three aggregates by hand; this plan replaces that idea with plan A's generated catalog. That
listener was verified end to end against keiro-ui through a Caddy proxy that strips the
`/keiro` and `/kiroku` prefixes, matching the deployment contract of `mori://tan/tan-keiro-ui`.
Commit `21d68bc` in the same repository is unrelated.

Terms used below. An "aggregate inspector" is a keiro value
(`Keiro.Inspection.Aggregate.AggregateInspector`, wrapped existentially as
`SomeAggregateInspector`) that tells keiro-ops how to load and display one aggregate type;
`AggregateInspectors` is a map from aggregate name to inspector built by
`Keiro.Inspection.Aggregate.aggregateInspectors :: [SomeAggregateInspector] -> Either Text
AggregateInspectors`. "Replay-audit targets" (`Keiro.ReplayAudit.SomeAuditTarget`) are
generated per aggregate category. A "validated projection catalog"
(`Keiro.Projection.Catalog.ValidatedProjectionCatalog`) describes read models and rebuild
groups. `Keiro.Ops.AppHooks` (from keiro-ops, defined in `Keiro.Ops.Embed`) bundles these for
the operations surface, with fields `workflowResume`, `timerFire`, `replayAudit`,
`projectionCatalog`, `aggregates`, `durableConsumers`, `processManagers`. Settei
(`mori://shinzui/settei`, 0.3.0.0) is the typed configuration library: a `Config a` declares
keys, a `Source` supplies raw values (built-in defaults, files, environment), and `Bindings`
map environment variable names to keys.

ADRs. [ADR 2](../adr/2-separate-keiro-project-seeds-from-domain-implementation.md) is the
governing record: the module seeds minimal compilable libraries and a brief, the blueprint
implements the domain, the seed does not implement an assembled runtime, reusable HTTP
plumbing (the health probes) is seeded with injected policy and "must work in a fresh seed",
and seed files become hand-owned. This plan extends that rule to inspection and records the
extension as a new ADR. [ADR 3](../adr/3-separate-managed-scaffold-nix-wiring-from-user-extensions.md)
keeps `flake.module.nix` unmanaged and limits the scaffold's Nix file to tools, so this plan
does not touch Nix. [ADR 7](../adr/7-keep-service-images-unmanaged-and-use-nix2container-transports.md)
keeps service images in the unmanaged `flake.module.nix`, so exposing port 9094 in an image is
documented, not generated; it also records that Seihou dependency bindings are part of a
dependency's identity (see the last Decision Log entry).
[ADR 5](../adr/5-share-one-checked-runtime-scope-and-verify-managed-adoption.md) explains the
bare-shell versus retained-runtime split. Cross-repository: `mori://shinzui/keiro/okf/adrs/concepts/ADR-53`
(the HTTP surface reuses keiro-ops commands with bounded inspection work, schema agreement and
explicit mutation confirmation), `mori://shinzui/kiroku/okf/adrs/concepts/ADR-18` (the Kiroku
inspection surface is composable and self-describing), and
`mori://shinzui/jinmyaku/okf/adrs/concepts/ADR-14` (keiro-ops schema checks require PostgreSQL 18).

### Milestone 1: the seed compiles the inspection surface

Add two variables to `modules/haskell/haskell-keiro-project/module.dhall`:
`inspection.enabled-default` (type `bool`, default `"false"`, not prompted, description: "Built-in
default of the generated server's inspection.enabled setting; deployments override it with
INSPECTION_ENABLED") and `inspection.port` (type `text`, default `"9094"`, not prompted,
validation `[1-9][0-9]{0,3}|[1-5][0-9]{4}|6[0-4][0-9]{3}|65[0-4][0-9]{2}|655[0-2][0-9]|6553[0-5]`
so only 1 to 65535 passes; Seihou compiles the pattern as a whole-value POSIX regex). Do not
add prompts: the defaults are the right answer for direct users and recipes pass values.
Change the `haskell.index-state` default to `INDEX_STATE` in both the module and
`blueprints/haskell-keiro-service/blueprint.dhall`, and the matching literal in
`scripts/check-keiro-bootstrap.py`.

Add seed steps and templates. In core, `files/inspection-catalog.hs.tpl` renders
`{{project.name}}-core/src/{{project.namespace}}/Inspection.hs`, the starter-owned re-export
module, in its seed form: it exports the four names with plan A's types and defines an empty
catalog (`aggregateInspectorCatalog = []`, `aggregateInspectors` from
`Aggregate.aggregateInspectors []` where `Keiro.Inspection.Aggregate` is imported
`qualified as Aggregate` because its function has the same name as the exported value,
`inspectionAuditTargets = []`, `inspectionProjectionCatalog` from `validateProjectionCatalog
emptyProjectionCatalog`), with a header comment that says to replace the body with the domain
form after the first scaffold that emits `Generated.Inspection` (a context with neither
aggregates nor projections emits none).
List it in `core.cabal.tpl` and add the `keiro` dependency bounded to `A_VERSION`'s major.

In server, port the reference modules into templates (rename `ChapterServiceV2` to
`{{project.namespace}}`, `chapter` to `{{project.name}}` in the listener's log line):
`files/inspection.hs.tpl` to `Server/Inspection.hs`, `files/inspection-hooks.hs.tpl` to
`Server/Inspection/Hooks.hs`, `files/inspection-listener.hs.tpl` to
`Server/Inspection/Listener.hs`, `files/inspection-origin.hs.tpl` to
`Server/Inspection/Origin.hs` (unchanged logic), and a new `files/inspection-settings.hs.tpl` to
`Server/Inspection/Settings.hs`, all under `{{project.name}}-server/src/{{project.namespace}}/`.
The behavioural changes from the reference are these. `Hooks.hs` imports

## Idempotence and Recovery

Rendering is repeatable: the check script renders into fresh temporary directories and also
asserts that rerunning the same command leaves files unchanged. The live script keeps its
fixture and logs under the printed temporary path and always stops the database it starts;
deleting that directory is the full cleanup. The scratch keiro-dsl directory can be deleted and
reinstalled. If the acceptance executable is started by hand, save its PID as shown and stop it
with `kill`; never stop processes by name.

All new project files are seeds. A project generated from 0.5.0 owns them, and later updates
never overwrite them. Projects generated from earlier versions do not receive changes to their
existing seeds (Cabal files, brief, README, justfile, `mori.dhall`), so `seihou update
haskell-keiro-project` cannot wire inspection into them; Seihou is expected to create the new
seed files at their absent paths, where they are inert until listed in Cabal. Milestone 4
observes the real behaviour and documents it in the module README together with the manual
adoption path (copy the modules, list them, add dependencies, wire `withInspection`), which
plan D exercises on the reference service. If a step in the module files goes wrong, revert the
working-tree change with Git; no published artefact changes until the registry version is
bumped and pushed.

```haskell
-- <name>-core: the starter-owned re-export (seed form: empty catalog).
module <Ns>.Inspection
  ( aggregateInspectorCatalog   -- :: [SomeAggregateInspector]
  , aggregateInspectors         -- :: AggregateInspectors
  , inspectionAuditTargets      -- :: [SomeAuditTarget]
  , inspectionProjectionCatalog -- :: ValidatedProjectionCatalog
  )

-- <name>-server
module <Ns>.Server.Inspection.Settings
  ( InspectionSettings (..)   -- { enabled :: Bool, host :: Text, port :: Int, allowedOrigins :: [Text] }
  , inspectionConfig          -- :: Settei.Config InspectionSettings
  , inspectionDefaults        -- :: Settei.Source  (built-in; rendered from the module options)
  , inspectionBindings        -- :: Settei.Env.Bindings
  , inspectionStoreSettings   -- :: ConnectionSettings -> ConnectionSettings  (poolSize 1, statementTimeout 2 s)
  )
module <Ns>.Server.Inspection
  ( withInspection            -- :: InspectionSettings -> ConnectionSettings -> IO a -> IO a
  , inspectionApplication     -- :: ConnectionSettings -> [Text] -> (Application -> IO a) -> IO a
  )
module <Ns>.Server.Inspection.Hooks (operationsHooks) -- :: Keiro.Ops.AppHooks
```

The contract for plan C and any other composing recipe is: depend on `haskell-keiro-project`
0.5.0 or newer and pass `inspection.enabled-default` (`"true"` or `"false"`, default `"false"`)
and `inspection.port` (decimal 1 to 65535, default `"9094"`). These set the built-in defaults of
the settings `inspection.enabled` and `inspection.port`; the other settings are
`inspection.host` (default `127.0.0.1`) and `inspection.allowedOrigins` (comma-separated
explicit HTTP(S) origins, default empty, which refuses browser WebSockets). At runtime
`INSPECTION_ENABLED`, `INSPECTION_HOST`, `INSPECTION_PORT` and `INSPECTION_ALLOWED_ORIGINS`
override them. A deployment reached from another container or pod must set `INSPECTION_HOST`
(for example `0.0.0.0`) and expose the port in its own unmanaged image definition. Composing
modules should note FRIC-10: adding a new variable binding to an already released dependency
entry, such as tan-keiro-bootstrap's dependency on this module, breaks `seihou update` for
projects created before the binding was added.
